1 · The synchronized detection pair, as a module

Strong

Files

  • ros/lidar_to_camera_solver/lidar_to_camera_solver/main.py
  • ros/lidar_to_lidar_solver/lidar_to_lidar_solver/main.py
  • ros/extrinsic_solver_node/extrinsic_solver_node/main.py (deleted at Stage 3)
  • ros/lctk_launch/launch/calibrate.launch.py

Problem

Every solver node wires conflux by hand: build a ROS2Synchronizer, register two subscriptions, register a callback, cache the newest pair, and interpret what an absent pair means. The interface each node presents to itself is large — synchronizer, statistics, drop policy, window, cached pair, cached timestamps — and the behaviour behind it is real: epoch detection, staleness, skew, and diagnosis.

Today's two defects were fixed in one of the three. lidar_to_lidar_solver is launched with sync_tolerance_ms: 0.0 hardcoded at calibrate.launch.py:285 — the infinite window that pairs by arrival order — and it has no epoch reset, so a replayed bag still stops it dead. The knowledge exists; it just has nowhere to live.

Shallow today: interface ≈ implementation

interface the node must know: 9 params, 2 topics, 4 counters, private _sync
implementation: a few caches

Deep: small interface, real behaviour

latest_pair(now) · stats_line()
conflux ownership · window policy · epoch reset · staleness gate · skew measurement · refusal diagnosis

Solution

One module that owns "give me the freshest pair of detections that were genuinely simultaneous." It takes a node and two topics, and answers either a pair or the reason there isn't one. The synchronizer, the window, the epoch reset, and the private _sync handle all move behind it.

Benefits

  • Locality — the next sync defect is fixed once. Today it was fixed once and left broken twice.
  • Leverage — a solver node learns two calls instead of nine parameters plus conflux's ordering contract.
  • Tests — the pure decision functions I added (should_reset_for_new_epoch, sync_wait_diagnosis, sync_pair_staleness_error) stop being loose functions in a 2187-line node and become the module's own test surface, exercised through the interface rather than beside it.
  • The reach into sync._sync becomes an internal seam instead of a private attribute touched from a node.

2 · The detection buffer, as a module

Strong

Files

  • ros/lidar_to_camera_solver/lidar_to_camera_solver/main.py (10 service callbacks, ~900 lines)
  • ros/lidar_to_camera_solver/test/test_placement_counting.py
  • ros/lidar_to_camera_solver/test/test_pose_weighting.py

Problem

The buffer of board placements is the node's central domain concept — it decides whether a capture constrains the extrinsic at all — but it has no interface. It is a bare list plus a lock plus ten service callbacks that each mutate it and format a response. The rules that matter (a frame is a duplicate placement; a solve needs N distinct placements; the covariance weights the fit) are spread across those callbacks.

The tests admit it. They cannot construct the module, so they reach past it: 

_count_placements = S._count_placements          # unbound method, fake self
w_tight = S._pose_weight(tight, corners)         # static reach-through
solver = S.__new__(S)                            # construct without __init__
rvec_w, tvec_w = S._refine_pnp_weighted(...)

The interface is the test surface. When tests need __new__ to dodge the constructor, the module is the wrong shape — not the tests.

Solution

A module holding the placements and the solve, with no rclpy import — the same rule that already makes board_geometry.py and detection_format.py testable. Adding a pair returns a result the caller can render (accepted / duplicate placement / solved with this quality); the service callbacks become the thin adapters they should have been.

Benefits

  • Locality — the "is this a new placement?" rule lives once, not in every callback that reports it.
  • Leverage — Stage 2's continuous mode needs exactly this module and nothing else from the node.
  • Tests — the existing reach-through tests become ordinary calls, and the deletion test passes: delete it and the placement rules scatter back across ten callbacks.

3 · Board visualisation out of the detector node

Worth exploring

Files

ros/lidar_board_detector/src/main.rs — lines 2348–2931

Problem

584 of the node's 3094 lines build RViz markers: bbox markers, board markers, plane markers, ICP correspondence markers, per-iteration debug poses. It is pure geometry-to-message code with no ROS behaviour beyond the message types, yet it sits inside the node struct and so has no test at all. Phase 1's frame change had to be verified by an operator looking at where an arrow pointed — that is exactly the code that draws the arrow.

Where the 3094 lines go

params/config 450
detection pipeline 620
markers 584
cloud decode 300
covariance 350
the rest

Solution & benefits

A module that turns a board detection plus a header into the marker arrays. Interface: one call per visual. Locality: the marker geometry stops being interleaved with publishing. Tests: marker positions become assertable — the corner-aligned frame could be pinned in a unit test instead of by eye.

4 · PointCloud2 decoding as one module

Worth exploring

Files

  • ros/lidar_board_detector/src/main.rs (convert_pointcloud2_to_points, read_coord)
  • ros/pointcloud_image_overlay/pointcloud_image_overlay/overlay_node.py
  • rust/board-cluster-detector/src/background.rs

Problem & solution

Field offsets, datatypes, endianness and point striding are decoded in three places across two languages. Two adapters means a real seam — this one has three. A malformed-cloud bug fixed in the detector is not fixed in the overlay. One decoding module per language, with the field-layout rules behind it, and the callers stop knowing what point_step means.

Weaker than 1 and 2 because the duplication is stable and low-churn — worth doing when one of these files is next opened, not as its own campaign.

5 · The detection pipeline as a value, not a procedure

Speculative

Files

ros/lidar_board_detector/src/main.rs — process_pointcloud, lines 904–1218

Problem & solution

A 300-line procedure that filters, fits a plane, runs ICP, scores the fit, and publishes eight debug topics along the way — with early returns that publish an empty detection array. The publishing is braided through the decision-making, so the decisions can't be tested and the reject reasons can only be read from logs.

Deepening it means returning a result — detection or rejection-with-reason, plus the debug artefacts — and letting the node publish. Marked speculative because docs/superpowers/plans/2026-07-28-boarddet-reject-reason-diagnostics.md is already in flight over this area; it should absorb this rather than compete with it.

Top recommendation — candidate 1

Take the synchronized detection pair first, because the argument for it is not hypothetical: the two defects fixed today still exist in lidar_to_lidar_solver, which is launched with the infinite window at calibrate.launch.py:285 and has no epoch reset. That is what missing locality costs, stated in a bug rather than in principle.

It is also the cheapest of the two strong candidates: the behaviour is already written and already tested as pure functions — it needs a home, not an invention. Candidate 2 is the better follow-up, and Stage 2 of the diamond-frame work will want it anyway.
